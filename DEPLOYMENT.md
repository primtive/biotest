# Production на vps-msk

> Ниже описана работающая конфигурация production. Следующая версия `new2` подготовлена в репозитории и отдельном дампе, но по просьбе владельца **на VPS не установлена**. В новой версии вход только по логину; описанный ниже пароль относится к текущему production.

Развёрнуто 20 октября 2026 года (МСК). Сайт: https://orenbio.ru.

## Что было исправлено на сервере

До настройки контейнер приложения запускался, но MongoDB отсутствовала. В `DATABASE_URL` был указан недоступный хост `mongo`. Caddy не запускался: `/root/Caddyfile` был каталогом, а контейнер ожидал файл.

Предыдущие `.env`, `compose.yml`, каталог `Caddyfile` и сведения об образе/контейнере сохранены в `/root/biotest-backups/pre-deploy-20261019T211141Z`. Исходный старый дамп `/root/biotest-dump-30.05.26` не изменялся. Ранее работающей базы на VPS не было.

## Работающая конфигурация

На VPS рабочая директория Compose — `/root`, имя проекта — `biotest-prod`. Фактическая конфигурация находится в `/root/compose.yml`, `/root/Caddyfile`, `/root/.env`. Корневой `compose.yml` репозитория предназначен для внешней MongoDB; серверная конфигурация дополнительно содержит локальный сервис MongoDB и использует готовый образ приложения.

| Сервис | Версия / образ | Назначение |
| --- | --- | --- |
| app | `primtive/biotest:deploy-20261020-60b5c1310c72` | Уже загруженный образ `primtive/biotest:latest`, ID `60b5c1310c72`; Next.js 15.5.28. Образ не пересобирался и не заменялся скачиванием. |
| mongo | MongoDB 8.0.34, `mongo@sha256:4a4ab5d4834207389e0d7270fac988e21ffedccecba77991a552f755df229907` | Постоянный том `biotest-prod_mongo_data`, база `biotest_v2`, replica set `rs0`. |
| caddy | Caddy 2.11.7, `caddy@sha256:d8542f48d34a9cf4e4c11a478865229840e87e4c96ea3f439101f31a5d35f75f` | HTTPS, автоматическое получение и обновление сертификата, HTTP → HTTPS, сжатие, передача SSE без задержки. |

Приложение работает от пользователя `node`. Все сервисы имеют `restart: unless-stopped`; Docker включён в автозапуск. Приложение проверяет доступность MongoDB и HTTP в healthcheck, MongoDB имеет отдельный healthcheck. Логи Docker ограничены тремя файлами по 10 МБ на сервис.

Извне доступны SSH 22/TCP, HTTP 80/TCP и HTTPS 443/TCP+UDP. Порты приложения 3000 и MongoDB 27017 на хост не публикуются. Caddy и приложение соединены сетью `web`; MongoDB и приложение — закрытой сетью `data` с `internal: true`.

Для VPS с 2 ГБ RAM кэш WiredTiger ограничен 0,35 ГБ, oplog — 256 МБ. Лимит открытых файлов MongoDB установлен в 64000 ([рекомендации MongoDB](https://www.mongodb.com/docs/manual/reference/ulimit/)). Это одна нода replica set: транзакции поддерживаются, отказоустойчивости между серверами нет. Перезагрузка всего VPS не выполнялась; сохранность данных при пересоздании контейнера MongoDB проверена.

## Доступ администратора

В исходном дампе у пользователей **нет паролей**. В новой версии вход требует пароль. Для первого входа создан `prod-admin` со случайным паролем; получить его можно по своему SSH-доступу:

```sh
ssh vps-msk 'cat /root/biotest-secrets/admin-credentials.json'
```

Файл имеет права 0600. Пароль не включён в репозиторий или этот документ. Через `/admin/users` можно назначать пароли существующим пользователям.

## Проверки

Проверены публичный DNS, редирект HTTP 308 → HTTPS, доверенный сертификат Let's Encrypt и открытие страницы входа в браузере. Выполнены 20 функциональных проверок через настоящий HTTPS: вход администратора, защищённая сессия, отказ во входе без пароля, ограничения API/админки, основные страницы, статистика, отклонение запросов с чужого Origin, SSE и ограниченные права пользователя MongoDB. Проверены чтение новой схемы и транзакция Prisma.

## Резервная копия и обслуживание

Создан полный архив MongoDB с oplog: `/root/biotest-backups/database/biotest-20261019T211652Z.archive.gz`. Архив проверен `mongorestore --dryRun`, рядом находятся SHA-256 и журнал. Фактическое восстановление этого полного архива не выполнялось. Это отдельная копия от исходного мигрированного дампа, включающая созданного администратора и пользователей авторизации MongoDB.

Повторное резервирование:

```sh
ssh vps-msk '/root/biotest-backup.sh'
```

Скрипт создаёт архив с правами 0600, не выводит пароли и проверяет разбор архива. Автоматическое расписание и хранение вне VPS не настроены.

Состояние и логи:

```sh
ssh vps-msk 'cd /root && docker compose ps'
ssh vps-msk 'cd /root && docker compose logs --tail 100 app caddy'
```

Повторный запуск:

```sh
ssh vps-msk 'cd /root && docker compose up -d --wait'
```

Для обновления приложения сначала сделать резервную копию, загрузить новый образ и указать его отдельный тег в `APP_IMAGE` в `/root/.env`. Затем выполнить `docker compose up -d --no-deps --wait app`. Для возврата предыдущего совместимого приложения вернуть прежний тег. Восстановление базы следует сначала проверять в отдельной MongoDB, а не импортировать поверх работающей базы. Не выполнять `docker compose down -v`: этот параметр удаляет постоянные тома.
