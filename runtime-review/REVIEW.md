## Подтверждённые проблемы высокого приоритета

P1 — раскрытие данных, обход прав либо нарушение достоверности результатов. P2 — существенная ошибка расчёта, производительности или обработки входных данных.

### R01 · P1 · Анонимный запрос `/admin/users` раскрывает всех пользователей

**Проверка.** Запрос без cookie и без автоматического следования redirect возвращает HTTP 200. В ответе есть `NEXT_REDIRECT`, но одновременно сериализованы документы всех 302 пользователей исходного дампа. Во время проверки присутствовали четыре UI-фикстуры: всего в ответе 306 пользователей и 12 073 записи начислений. Повтор с заголовком `RSC: 1` дал тот же результат. Объём ответа — около 1,36 МБ HTML либо 1,21 МБ RSC.

**Последствия.** Перенаправление в браузере не защищает уже переданные данные. Раскрываются логины, имена, административный статус, группы, даты, история начислений и связанные идентификаторы тестов. Поле `password` также присутствует в форме документа, но непустых значений в проверенном ответе нет; раскрытие существующих паролей не утверждается.

**Причина.** Страница выполняет `getUsers()` и передаёт полные документы клиентскому компоненту. Проверка администратора расположена только в шаблоне родительского сегмента и не останавливает формирование данных дочерней страницы.

**Что исправить и проверить.** Проверять сессию и роль внутри серверной операции чтения до запроса данных; отдавать клиенту только разрешённые поля. Для анонимного и обычного пользователя ни HTML, ни RSC не должны содержать пользовательские документы, даже при redirect. Тест должен исследовать тело ответа.

Код: [страница пользователей](/Users/alexey/dev/biotest/app/admin/users/page.tsx:9), [запрос полных документов](/Users/alexey/dev/biotest/data/users.ts:4), [проверка в шаблоне](/Users/alexey/dev/biotest/app/admin/template.tsx:12). Доказательство: `read-only.results.json`, первые два результата.

### R02 · P1 · Административные изменения выполняются без сессии

**Проверка.** Без cookie получены HTTP 200 и подтверждённые изменения БД для следующих действий:

| Операция над собственной фикстурой | Результат |
|---|---|
| Создание пользователя с `admin: true` | Создан администратор |
| Изменение обычного пользователя на `admin: true` | Роль изменена |
| Создание темы | Тема создана |
| Создание задания | Задание создано |
| Ручное начисление `543` очков | Баланс и журнал изменены |
| Удаление созданного задания | Задание удалено |

Контрольные запросы чтения `/api/tasks` и `/api/reports` без сессии возвращают 403. Значит, защита есть у отдельных GET, но отсутствует у проверенных изменяющих маршрутов.

**Что исправить и проверить.** Общая серверная проверка сессии и административной роли для всех административных операций; явные входные схемы вместо передачи произвольного JSON в Prisma. Обычный пользователь не должен изменять свою роль через API. При 401/403 состояние БД должно оставаться прежним.

### R03 · P1 · Знания логина достаточно для входа администратором

**Проверка.** Вход через штатные CSRF/credentials endpoints выполнен для синтетического ученика и администратора. Пароль не отправлялся. Ответ сессии подтвердил соответствующего пользователя и `admin: true` для администратора.

### R04 · P1 · Ответ записывается в чужой завершённый тест с подменой задания

**Проверка.** Без сессии отправлен ответ в собственную фикстуру, моделирующую чужой уже завершённый тест. Задание в URL и `id` в JSON различались. Сервер вернул 200 и `correct: true`, проверил ответ по URL, но сохранил ID из тела. Сохранённое задание вообще не входило в `tasksIds` теста. Повтор того же запроса создал второй ответ.

**Последствия.** Можно изменять завершённую историю и добавлять произвольные, повторные ответы. Статистика, использующая массив ответов, перестаёт соответствовать составу теста.

**Что исправить и проверить.** Устанавливать пользователя по сессии, проверять владельца и состояние попытки, брать идентификатор задания из одного источника и проверять принадлежность попытке. Обеспечить не более одного результата на пару «попытка — задание». Повтор одинакового запроса должен быть идемпотентным либо давать явный конфликт без дополнительной записи.

Код: [обработчик ответа](/Users/alexey/dev/biotest/app/api/tasks/[id]/complete/route.ts:23). Доказательство: `unauthenticated_mismatched_answer_to_completed_foreign_test`, `duplicate_answer_submission`.

### R05 · P1 · Параллельные ответы теряются при HTTP 200

**Проверка.** Одновременно отправлены ответы на 12 разных заданий одной фикстуры. Все 12 запросов вернули 200 и правильный ответ. В сохранённом в этом запуске результате осталось два ответа, десять потеряно. Итоговое число зависит от расписания конкурирующих записей; существенен факт потери успешно принятых ответов.

**Причина.** Каждый запрос читает массив, дописывает в память и заменяет весь массив. Последующий запрос перезаписывает изменения предыдущего.

**Что исправить и проверить.** Использовать атомарную модель записи с защитой от повторов. Конкурентный тест должен сохранять все 12 различных результатов, а повтор одного задания не должен добавлять дубликат. Блокировка кнопки на клиенте полезна для UX, но серверную гонку не устраняет.

Код: [чтение и перезапись массива](/Users/alexey/dev/biotest/app/api/tasks/[id]/complete/route.ts:31). Доказательство: `concurrent_distinct_answers`.

### R06 · P1 · Повторное завершение повторно выдаёт очки

**Проверка.** Два анонимных POST завершения одной попытки с двумя правильными ответами вернули 200. После первого вызова: 2 очка, один тест и одна запись журнала. После второго: 4 очка, два теста и две записи с тем же `testId`.

**Что исправить и проверить.** Завершение должно быть однократным переходом состояния с атомарной фиксацией результата. У одного теста может быть одно начисление. Повторные и одновременно пришедшие запросы, обновление страницы и сетевой retry не должны изменять уже выданные очки.

Ошибка воспроизведена и обычным действием в браузере: после успешного прохождения двух заданий повторное открытие исходного URL `/t/{id}` увеличило очки с 2 до 4, счётчик тестов с 1 до 2 и создало вторую запись того же теста. Клиентский эффект автоматически вызывает завершение, когда количество уже сохранённых ответов равно числу заданий.

Код: [завершение теста](/Users/alexey/dev/biotest/app/api/complete/[id]/route.ts:11), [клиентский эффект](</Users/alexey/dev/biotest/app/(req auth)/t/[id]/test.tsx:43>). Доказательства: `unauthenticated_repeat_completion`, `ui.results.json` → `reopen_completed_test_in_browser`.

### R07 · P1 · HTTP 500 оставляет попытку частично завершённой

**Проверка.** Завершение попытки без ответов возвращает 500, но `isComplete` уже становится `true`, а `completedAt` записан. Счётчик пользователя и журнал начислений остаются прежними. Воспроизведено и для попытки с двумя назначенными заданиями без ответов, и для пустой попытки.

**Причина.** Сначала сохраняется завершение, затем выполняются расчёт и обновление пользователя. При нулевом знаменателе расчёт процента ломается после первой записи. Это подтверждённое частичное сохранение, а не только предположение о возможной ошибке сети.

**Что исправить и проверить.** Проверять допустимость завершения до изменений; явно определить поведение незаполненной и пустой попытки. Сохранять состояние, результат и начисление атомарно. При любой ошибке не должно оставаться завершённого теста без согласованного результата. Если прогресс обновляется отдельно, нужна восстанавливаемая очередь или другой явный механизм доведения агрегатов.

Код: [первая запись](/Users/alexey/dev/biotest/app/api/complete/[id]/route.ts:11), [деление и обновление пользователя](/Users/alexey/dev/biotest/app/api/complete/[id]/route.ts:70). Доказательство: `completion_with_no_answers_partial_commit`, `zeroAnswerCompletion`.

### R09 · P2 · Неупорядоченный ответ теряет повторяемость символов

### R11 · P2 · Конец периода отчёта ограничен полуночью; часовой пояс не определён

Отчёт за `from=2026-05-20&to=2026-05-20` включил только фикстуру ровно в `00:00Z`: один тест и два очка. На этих данных полный UTC-день содержит три теста и девять очков; 20 мая по Москве — три теста и шесть очков. Замена `to` на следующий день включает три UTC-теста, но всё ещё не выражает московский календарный день. Отдельная фикстура в полдень 1 января 2099 года не попадает в однодневный отчёт и появляется при `to=2099-01-02`.

Зафиксировать часовой пояс отчёта и преобразовывать выбранные календарные даты в полуинтервал `[начало первого дня, начало следующего за последним дня)`. Проверять границы суток и переходы дат. Отдельно определить, отчёт измеряет время начала или завершения: текущая фильтрация использует `createdAt`.

Код: [границы периода](/Users/alexey/dev/biotest/app/api/reports/route.ts:54). Доказательства: `reportsingleDay`, `reporttwoDays`, `report_excludes_selected_end_day`.

### R12 · P2 · Незавершённые тесты меняют среднее число правильных ответов

Для четырёх завершённых попыток с десятью правильными ответами и одной незавершённой без ответов личный график содержит среднее `2`, тогда как среднее по завершённым — `2,5`. Текущий код делит сумму правильных ответов всех попыток на количество всех попыток. Один лишь запуск нового теста снижает показатель.

Определить знаменатель и подпись показателя; если это среднее результата завершённого теста, фильтровать числитель и знаменатель по завершённости. Ту же формулу согласовать с административной страницей пользователя.

Код: [накопление](</Users/alexey/dev/biotest/app/(req auth)/stats/page.tsx:41>), [деление](</Users/alexey/dev/biotest/app/(req auth)/stats/page.tsx:73>). Доказательство: `personalChartUnfinished`.

### R14 · P2 · Параметры пагинации и идентификаторы приводят к необработанным ошибкам

| Запрос | Наблюдение |
|---|---|
| `/api/tasks?page=0`, `page=-1`, `page=foo` | HTTP 500, пустое тело |
| `/api/tasks?topics=invalid` | HTTP 500 |
| `/admin/history?page=-1` | HTTP 200 с `PrismaClientUnknownRequestError` в RSC: недопустимый `skip` |
| `/t/invalid/review` | HTTP 200 с Prisma-ошибкой `Malformed ObjectID` в RSC |
| Отчёт с `from > to` | HTTP 200, возвращены пользовательские строки вместо отказа |
| Отчёт с `topicGroup=unknown` | HTTP 200, пустые данные вместо ошибки параметра |

При этом отсутствие дат и некорректная дата отчёта правильно возвращают 400; это положительные контрольные случаи. Неизвестный корректно сформированный ID просмотра теста дал пустую страницу без явного «не найдено».

Нужна общая валидация параметров: конечное положительное целое для номера страницы, допустимые ObjectId и значения enum, согласованный диапазон дат. Ошибки пользовательского ввода должны давать предсказуемые 400/404, а страницы — понятное состояние без Prisma-ошибки. Не путать HTTP-код уже начатого RSC-потока с успешным результатом рендера.

## Производительность и архитектура статистики

Пять последовательных прогретых запросов на локальном dev-сервере; время включает чтение полного тела ответа. Данные находятся в локальной MongoDB, сетевой задержки production нет. **Подтверждённые причины лишней работы.**

- `explain` запроса истории пользователя: просмотрено 13 719 документов, прочитано ноль ключей индекса, возвращено 342 документа, верхний этап `SORT`. Число документов включает временные фикстуры этого запуска. Личная выборка просматривает всю коллекцию вместо индексного диапазона.
- Аналогичный pipeline отчёта с `$lookup` занял около 726 мс по MongoDB execution statistics. Просмотрено 310 пользовательских документов, возвращено 189 строк. Это измерение pipeline, не доказательство конкретного числа просмотренных тестов: использованная версия MongoDB не вывела такие счётчики для `$lookup` в сохранённой сводке.

Пересчёт прогресса повторно читает всю завершённую историю и делает отдельный последовательный запрос задания для каждого правильного ответа по каждой затронутой теме. Последний путь подтверждён чтением кода, но его задержка на максимальной исходной истории в этом этапе не измерялась.
